# pwiz-symlink-fix

A drop-in replacement for the official ProteoWizard / Skyline Docker image that
fixes a regression in which msconvert and Skyline silently mis-read input files
accessed through symbolic links. Tailored for our workflow (Skyline + msconvert
+ BlibBuild, all vendor formats), so it ships smaller than upstream while
keeping every feature we use.

## The problem

In May 2026 the ProteoWizard container repo
([commit 489b8c0](https://github.com/ProteoWizard/container/commit/489b8c0))
switched its WineHQ branch from `devel` to `staging` (Wine 7.8 → 10.6) to chase
a Thermo performance improvement. Wine-staging carries a large set of
out-of-tree patches that mainline Wine does not. One of them
(`patches/ntdll-Junction_Points/`) makes Wine lie to Windows applications about
symbolic links: any path-based file-metadata API
(`GetFileAttributesEx`, `FindFirstFile`, `.NET FileInfo.Length`, etc.) reports
a symlink as a 0-byte file with the reparse-point flag set, even when the link
target is megabytes or gigabytes of valid data.

Many vendor SDKs (Thermo RawFileReader, Bruker CompassXtract, Waters RawData,
Agilent MassHunter, Sciex) follow the pattern *"ask the file size by path,
then open and seek to size minus N to read a footer/index."* Given a 0-byte
size by mistake, they bail out before ever opening the file. The same is true
for `.NET FileInfo.Length`, which Skyline calls. Vendor directory bundles
(Bruker `.d`, Waters `.raw`, Agilent `.d`) also break when their internal
component files are themselves symlinks — a real scenario for
`archivemount`-tar'd or NFS-staged data.

**This means**: with the published 2026-05 image, mounting host data through
a symlink (very common in HPC / shared-storage workflows) silently produces
wrong results.

The full empirical diagnosis — including the three specific wine-staging
patches at fault, a refined probe that isolates the bug to *path-based*
metadata APIs only (handle-based queries are unaffected), and end-to-end
verification on the published pwiz image — is in
[`docs/wine-symlink-regression.txt`](docs/wine-symlink-regression.txt).

## The fix

Three approaches were considered (see
[`docs/wine-symlink-regression.txt`](docs/wine-symlink-regression.txt) for details).
This project implements the third and cleanest:

1. **Switch WineHQ branch back to `devel` at the same Wine version, in a
   derived image.** Smallest possible change but bloats the image to ~10 GB
   because the staging-era files in the upstream layers are shadowed, not
   removed. (We shipped this first as `pwiz-fixed-devel`; superseded.)
2. **Upgrade wine-staging to v10.19+** where the offending patchset is
   disabled upstream. Requires bumping the base image past `ubuntu:20.04`,
   touches more than the bug.
3. **Rebuild the official image from source with `WINEDISTRO=devel`,
   reusing the published image's pwiz/Skyline binaries.** Single-source
   image, no shadowed cruft, pruneable. **This is what we ship.**

While we're rebuilding from source, we also prune the pwiz tree to our
workflow:

- **Keep**: Skyline (Skyline-daily.exe), msconvert, BlibBuild, **all
  vendor SDKs** (Thermo, Bruker, Waters, Agilent, Sciex, Shimadzu).
- **Drop**: Skyline test fixtures (`CachedDownloadsForTests/`, ~123 MB),
  Skyline's bundled JRE + Java tools (`Tools_CFTKIC31_en-US/`, ~217 MB),
  Skyline debug symbols and test DLLs (~95 MB), and pwiz CLI tools we don't
  use — `msaccess`, `msbenchmark`, `mscat`, `msdiff`, `msdir`, `mspicture`,
  `peakaboo`, `qtofpeakpicker`, `txt2mzml`, `chainsaw`, `idconvert`,
  `idcat`, `msistats`, `pepcat`, `pepsum`, `seems`, `MSConvertGUI`
  (~120 MB).

The result:

| Image | Size |
|---|---|
| Upstream (broken, wine-staging) | 6.74 GB |
| Quick fix: derived devel + wineboot --update | 9.99 GB |
| **This project: fresh devel + workflow prune** | **6.13 GB** |

We also fix an unrelated, latent bug in the upstream image: the default
`CMD` is `["wine64_anyuser", "msconvert"]`, but modern Wine (any branch,
9.x+) merged wow64 and no longer ships a separate `wine64` binary, so the
upstream image fails out of the box with `sudo: wine64: command not found`.
We change the CMD to `["wine_anyuser", "msconvert"]`.

```
│   └── DOCKER-PLAN.md              — historical: how this build was designed
│
├── container/                      — clone of ProteoWizard/container, reference only
└── pwiz-artifacts/                 — generated by build.sh, gitignored
```

The four files at the project root (`build.sh`, both `Dockerfile.*`, `mywine`)
plus `docs/` are everything needed to rebuild the image. `container/` is a
frozen snapshot of the upstream repo at the regressing commit (`489b8c0`),
kept for reference; nothing in the build pipeline reads from it.

## Building the image

Prerequisites: Docker, ~10 GB free disk, network access to Docker Hub and
WineHQ apt repos.

```bash
./build.sh
```

That runs four stages:

1. **Build the wine-dotnet base** (~25–40 min on first run, ~0 s on re-runs).
   `winetricks -q dotnet48` is the slow step. Output:
   `local/wine-dotnet:winedevel10.6-net4.8-x64`.
2. **Extract pwiz binaries** from the published upstream image into
   `./pwiz-artifacts/`.
3. **Prune** the artifacts (see "The fix" above for what's kept vs. dropped).
   Expect ~395 MB after pruning.
4. **Build the final image**, tagged `pwiz-fresh-devel:latest` (~1 min).

The script is idempotent: re-running with the wine-dotnet base image and
`./pwiz-artifacts/` already present skips stages 1 and 2 and only rebuilds the
final image. To force a full rebuild:

```bash
docker rmi local/wine-dotnet:winedevel10.6-net4.8-x64
rm -rf ./pwiz-artifacts
./build.sh
```

To use a different final tag, set `FINAL_TAG`:

```bash
FINAL_TAG=my-namespace/pwiz:dev ./build.sh
```

## Smoke-testing the build

After `build.sh` finishes, verify the symlink fix and the major tools:

```bash
# 1. Symlink metadata fix (fast)
mkdir -p /tmp/symlink-test
printf 'HELLO\n' > /tmp/symlink-test/target.txt
ln -sf target.txt /tmp/symlink-test/link.txt
docker run --rm -v /tmp/symlink-test:/data pwiz-fresh-devel:latest \
    wine_anyuser cmd /v:on /c 'for %f in (Z:\data\link.txt) do @echo %~zf'
# Expected output: 6   (NOT 0)

# 2. Skyline-daily launches
docker run --rm pwiz-fresh-devel:latest \
    wine_anyuser /wineprefix64/drive_c/pwiz/skyline/Skyline-daily.exe --help \
    2>&1 | head -5

# 3. BlibBuild launches
docker run --rm pwiz-fresh-devel:latest \
    wine_anyuser /wineprefix64/drive_c/pwiz/skyline/BlibBuild.exe \
    2>&1 | head -5

# 4. msconvert reports correct version
docker run --rm pwiz-fresh-devel:latest wine_anyuser msconvert --help \
    2>&1 | grep "ProteoWizard release"
```

For an end-to-end test on real vendor data, point msconvert at a symlinked
`.raw`/`.d`/`.wiff`/`.lcd` file:

```bash
docker run --rm -v "$(pwd)":/data pwiz-fresh-devel:latest \
    wine_anyuser msconvert /data/symlink.raw -o /data
```

## Tagging and pushing

`build.sh` does **not** push. Tag and push manually so you stay in control of
which registry receives which build:

```bash
TAG="3.0.26120-bb3c999-fixed"

docker tag pwiz-fresh-devel:latest \
    mriffle/pwiz-skyline-i-agree-to-the-vendor-licenses:$TAG
docker tag pwiz-fresh-devel:latest \
    quay.io/protio/pwiz-skyline-i-agree-to-the-vendor-licenses:$TAG

docker push mriffle/pwiz-skyline-i-agree-to-the-vendor-licenses:$TAG
docker push quay.io/protio/pwiz-skyline-i-agree-to-the-vendor-licenses:$TAG
```

Note: this build does not share layer blobs with `proteowizard/...` on either
registry. Every layer is built from scratch, so push time scales with image
size (~6 GB), not with the delta. End users pulling for the first time
similarly pay the full size; pulling our updated image after a previous pull
of *the same tag* will dedupe normally.

## Updating to a newer pwiz/Skyline version

When ProteoWizard publishes a new `proteowizard/pwiz-skyline-i-agree-to-the-vendor-licenses`
image, rebuild against it:

```bash
docker pull proteowizard/pwiz-skyline-i-agree-to-the-vendor-licenses:latest
rm -rf ./pwiz-artifacts
./build.sh
```

(The wine-dotnet base does not need to rebuild — it tracks Wine, not pwiz.)
Then verify the new image's pwiz version:

```bash
docker run --rm pwiz-fresh-devel:latest wine_anyuser msconvert --help \
    2>&1 | grep "ProteoWizard release"
```

…and bump the registry tag accordingly when pushing.

If upstream ever switches WineHQ back to `devel` (or moves to wine-staging
v10.19+, where the offending patchset is disabled), this project becomes
unnecessary and you can go back to using the upstream image directly.
